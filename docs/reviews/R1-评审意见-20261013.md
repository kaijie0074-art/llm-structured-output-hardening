工程师提交的分层防御方向正确，指标达标。以下 6 条意见按优先级排列，处理结果见 [采纳记录](采纳记录.md)。

**意见 #1（必须改）**：`OptimizePipeline` 的重试目前把"上一次输出"的反馈写成了固定文案。重试不带具体错误信息等于让模型再盲猜一次。参考 instructor 的做法：把首次失败的原因（解析异常/schema 违规条目/越界 field）拼进重试 prompt。我看到代码里 lastFeedback 有三类文案，但 schema 违规只带了第一条 message——把命中的违规列表带全。

**意见 #2（必须改）**：`LenientRepair` 的中文引号替换，必须证明不会误伤字符串**值内部**的合法中文引号（简历语境里用户原文自带 "参与" 这类引用很常见）。当前测试没有这个用例，补一个：值含中文引号的 JSON 修复后内容必须原样保留。

**意见 #3（必须改）**：`FidelityGate.INFLATE_FACTOR=10` 和 `METRIC_FLOOR=100` 两个魔法数，代码里只有一行注释"10 倍为行业常用异常分界"。 unacceptable。写成常量并给出可辩护的依据：什么口径的润色合法、什么口径算造假，边界案例写清楚（例如 3000→30000 拦、3000→"约 3000"放行）。测试要覆盖两侧。

**意见 #4（建议）**：`ResultStore` 只有 save 和翻日志能力。生产要接监控，至少暴露：按 status 计数、分层触发计数、按 promptVersion 计数三个统计接口，写进接口契约注释。

**意见 #5（建议）**：eval 报告只有一个整体指标。黄金集本来就分了本科/大专两档（生成器里有 stratum 字段），报告里却没有分组呈现——均值会掩盖短板档位。加"分层×结果分布"表。

**意见 #6（已讨论，维持工程师判断）**：我质询过"捏造违规为何不重试"（万一模型第一次误伤呢）。工程师的回应：捏造被拒后重试，模型倾向换一种编法而非收敛，且 needsReview 人工队列成本低于多等一次 LLM。我接受该判断，但要求补充：needsReview 队列的产品侧 SLA 说明写进 design.md 的线上闭环节。（已完成，见 design.md。）
